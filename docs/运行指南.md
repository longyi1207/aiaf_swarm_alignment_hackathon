> Historical setup notes. For the current vLLM lesion backend and a clean post-cache-fix
> replication, use [CLEAN_REPLICATION.md](CLEAN_REPLICATION.md). The older backend
> restrictions and checkpoint-resume advice below do not apply to the new workflow.

## 黑客松精简版的顺序（方案 A）

一张 A100，详见设计 §8。

1. `uv run swarmtom run configs/run_qwen_smoke.yaml`：1 局冒烟，看速度和工具调用解析。
2. 剂量检查：`dose-gen` → `dose-judge` → `dose-report`（§5）。按报告修改 `configs/lesions.yaml` 里的 `tom` / `emp`，并定下 `enable_thinking`。
3. `uv run swarmtom run configs/run_phase0_lite.yaml`：16 局基线，看是否通过校准关卡。
4. `uv run swarmtom run configs/run_main_lite.yaml`：40 局主实验，适合整夜跑。
5. `uv run swarmtom score runs/main_lite`：评分。

每一步中断后，重新运行同一条命令即可续跑。

## 0. 连上机器

朋友的 Spark 用 Tailscale 共享，参考 NVIDIA 的官方 playbook：https://build.nvidia.com/spark/tailscale.md

1. 朋友在 Spark 上给你**单独开一个账号**。你把自己的 SSH **公钥**发给他，加进 `~/.ssh/authorized_keys`。**私钥不要给任何人。**
2. 你在 Mac 上装 Tailscale，接受朋友分享的机器，然后 `ssh 你的用户名@<spark 的 tailscale 名字>`。
3. 长任务一律放在 `tmux` 里跑，断线后进程不会停：

```bash
tmux new -s swarm
tmux attach -t swarm
```

## 1. 环境

Spark 是 ARM（aarch64）+ CUDA。**先确认 PyTorch 能看到 GPU**。GB10 的支持我没有核实过，这是上机后第一件要查的事。

```bash
git clone git@github.com:longyi1207/aiaf_swarm_alignment_hackathon.git && cd aiaf_swarm_alignment_hackathon
curl -LsSf https://astral.sh/uv/install.sh | sh      # 如果还没有 uv
uv sync --extra model --group dev
uv run python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

**一定要装 Qwen3.5 线性注意力的加速库。** Qwen3.5-9B 的 32 层里有 24 层是线性注意力，没有这两个库，transformers 会退回到慢速的 PyTorch 实现，整体可能慢好几倍：

```bash
uv pip install flash-linear-attention causal-conv1d
```

装好后，冒烟测试的日志里**不应该**出现 "fast path is not available" 一类的警告。

如果 `cuda.is_available()` 是 False，说明 uv 装到的 torch 没有带 CUDA。改用 NVIDIA 官方的 PyTorch 容器（NGC），在容器里 `pip install -e .`。

确认 GPU 可用之后：

```bash
uv run pytest -q
huggingface-cli download Qwen/Qwen3.5-9B           # 约 19 GB
```

**断网**：agent 的 `run_python` 工具默认断网（`protocol.python_network: block`）。每次运行前，运行器会在沙箱里试着连外网和解析域名；只要能连上，就拒绝运行。有两种断网方式：

- **A. 只给 Python 工具断网**：`block`，默认。Linux 上用 `unshare -rn`，为每次调用创建一个没有网卡的网络命名空间。DGX OS 基于 Ubuntu，Ubuntu 24.04 之后默认禁止普通用户创建用户命名空间，这时自检会报错，改用 B。
- **B. 整个运行放进断网容器**：`--network none`，模型权重从宿主机的 HF 缓存只读挂载。配置里设 `protocol.python_network: container`，自检仍会确认容器里确实连不上网。

  ```bash
  scripts/run_isolated.sh run configs/run_phase0_baseline.yaml
  ```

  镜像定义在 `docker/Dockerfile`，基于 NVIDIA NGC PyTorch。请选一个支持 GB10 的标签，用 `--build-arg NGC_TAG=...` 传入。**这个镜像还没在 Spark 上实测过。**

## 2. 第一次上机：先跑 1 局冒烟测试

```bash
HF_HUB_OFFLINE=1 uv run swarmtom run configs/run_qwen_smoke.yaml
```

跑完检查三件事：
1. `runs/qwen_smoke/progress.log`：每一步的批大小、生成耗时、tok/s。由此估算完整实验要跑多久。
2. **工具调用解析是否正常**。Qwen3.5 的工具调用格式我没能在本地验证；解析器同时支持 Qwen2.5/3 的 JSON 格式和 Qwen3-Coder 的 XML 格式。下面的命令统计"模型输出里有 `<tool_call>` 却没解析出调用"的次数：

   ```bash
   python - <<'EOF'
   import json, glob
   for f in glob.glob("runs/qwen_smoke/games/*/events.jsonl"):
       ev = [json.loads(l) for l in open(f)]
       m = [e for e in ev if e["type"] == "model"]
       bad = [e for e in m if "<tool_call>" in e["raw"] and not e["tool_calls"]]
       print(f, "model turns", len(m), "parse errors", sum(bool(e["parse_errors"]) for e in m), "unparsed", len(bad))
   EOF
   ```

   如果 `unparsed` 不为 0，把一条 `raw` 发给我，我来改 `src/swarmtom/llm/parse.py`。
3. 读一局的完整对话：`runs/qwen_smoke/games/<id>/state.json` 里的 `agents.<名字>.messages`，看 agent 是不是真的在用 pandas 联表、算规则、在权衡。

## 3. Phase 0 基线校准

```bash
uv run swarmtom run configs/run_phase0_baseline.yaml      # 中断后再运行同一条命令会从断点续跑
uv run swarmtom score runs/phase0_baseline                # 写 results/agents.csv、games.csv
```

- **批大小** `backend.batch_size`：Spark 有 128 GB，可以先试 16–32；显存不够（OOM）时会自动对半拆分。
- **调试**：可以加 `--max-ticks N`，跑 N 步就停，之后用同一条命令续跑。

通过标准见设计 §8：
- 分析正确率（`classification_accuracy`、`found_own_f`）≥ 70%；
- 举报率在 15%–85%；
- 推理里确实有权衡。

不满足就改场景，回到第 2 步。

## 4. 更快的基线（可选）：vLLM

只跑**不损伤**的基线时，可以在 Spark 上起一个 vLLM 服务（带前缀缓存，比 transformers 快很多），然后把配置里的 backend 换成：

```yaml
backend:
  type: openai_compat
  base_url: http://localhost:8000/v1
  model: Qwen/Qwen3.5-9B
  max_tokens: 2048
  temperature: 0.6
  concurrency: 32
  extra_body: {chat_template_kwargs: {enable_thinking: true}}
```

**有损伤的条件必须用 `type: hf`**，vLLM 做不了按 agent 的激活干预。同一组比较里的所有条件要用同一个后端，否则后端差异会混进结果。另外，断网容器（方式 B）里访问不到宿主机上的 vLLM，用 vLLM 时请用方式 A。

## 5. Phase 0b：剂量配平 + 决定思考模式

```bash
uv run --extra model swarmtom dose-gen   configs/dose_check.yaml   # GPU；中断后重跑同一命令会续跑
uv run --extra model swarmtom dose-judge configs/dose_check.yaml   # 给共情回答打 0–10 分
uv run swarmtom dose-report runs/dose_check                        # 生成 report.md / report.json
```

- **规模**：13 个损伤条件 × 思考关 / 开 × （216 + 20 + 30）题，共约 6,900 次生成。关思考时很快；开思考时每题最多约 1,000 个 token，较慢。可以先用 `limit: {tom: 108}` 把 BigToM 减半。
- **评审**：默认用同一个模型（不损伤、关思考）打分，这样任何 API 凭证都不用放到朋友的机器上。如果想用 Azure 的评审模型，就把 `runs/dose_check/generations.jsonl` 拷回你的 Mac，在 Mac 上用 `judge.type: openai_compat` 跑 `dose-judge`，`.env` 只留在你自己的机器上。
- **看报告**：打开 `report.md`，里面有每个条件的下降量和置信区间、建议配平的那一对强度、思考模式的结论。选定之后，把 `configs/lesions.yaml` 里的 `tom` / `emp` 改成选定的强度，并把游戏配置里的 `enable_thinking` 设成报告的结论。

## 6. 主实验

Phase 0b 剂量配平通过后再跑：

```bash
uv run swarmtom run configs/run_main.yaml
```

N（agent 数）、门槛、轮数、步数上限都在配置文件里，按硬件调整即可。
